# 01｜產品需求 PRD

## 一句話

給一首歌、一種感覺或一段聲音描述，Qualia FM 編排一段有聲音質地連結的私人節目，並讓使用者聽見、看懂「為什麼這首適合接下來」。[U1/U2/U3]

## 核心價值與非目標

核心不是人氣排行、曲風分類或一般聊天回覆，而是 **Hook of Feeling → 跨曲風配對 → 可解釋的 Bridge → 連貫 Show**。不是多人同步廣播，不做串流平台替代品，不做下載器、歌詞資料庫、社群動態、管理儀表板或音訊混音工具。

## 使用情境

深夜工作需要有連貫氛圍但不費心點歌；練舞前想找相似律動與音色；放空時不想閱讀長篇分析；正在聽歌時只想一鍵「更放鬆」而不中斷。通勤／開車情境只設計出發前設定及大按鈕收聽，不鼓勵行進中輸入。

## Domain 定義

| 詞彙 | 定義 | 不能混淆 |
|---|---|---|
| Seed | 使用者提供的歌曲、感覺或聲音描述 | URL 本身不是音訊、也不是取得所有權 |
| Sonic DNA | 空間感、情緒速度、音色、歌詞情境四面向 | 情緒速度不等於精確 BPM |
| Hook of Feeling | Seed 最主要的感覺鉤子 | 不等於副歌或最熱門片段 |
| seedBridge | 候選曲如何回應 Seed 的特定元素 | 主觀推薦，不冒稱聲學量測 |
| transitionBridge | 下一曲與實際前一曲的關係 | 調序／補位後必須重新檢查 |
| Segment | 一首曲目與其可選串詞，作為不可拆散的節目單位 | 播放實際仍分 speech / track phase |
| Show | 具有 Seed、順序、版本與多個 Segment 的節目單 | 未開始播放不代表已聽完 |

## 首版必須有的功能

| ID | 需求 | 完成條件 |
|---|---|---|
| FR01 | 三類 Seed 輸入 | 感覺／歌名藝人／聲音描述；保留輸入草稿 |
| FR02 | 四面向分析與感覺鉤子 | 文案可理解；未知維度顯示未知、不瞎補 |
| FR03 | 目標五首、跨曲風精準配對 | 每首一個具體 Bridge＋三個 vibe 詞 |
| FR04 | 曲目解析與驗證 | 找不到不冒用同名不同藝人；有限補位、版本辨識 |
| FR05 | DJ 串詞 | 繁中 ≤80 字；明示 AI 聲音；可跳過、可關閉 |
| FR06 | 播放控制 | 播放／暫停／下一首／重新播放本曲；錯誤可恢復 |
| FR07 | 現在與接下來 | 不用換頁就知道正在播什麼，以及下一首的連結 |
| FR08 | 節目單 | 查看五首、單首移除與復原；不拆散 Segment |
| FR09 | 微調氛圍 | 使用者提交偏好後只替換未播放的下一批，不打斷當前曲 |
| FR10 | 手機 UI／PWA | 單手主操作、safe-area、鍵盤避讓、完整各種狀態 |
| FR11 | Provider 能力呈現 | mock／授權音源／Spotify／外連各有真實標示 |
| FR12 | 安全與成本 | key 後端、取消／timeout／上限；不得無限 LLM 循環 |

FR09 為本次新增的手機互動決策：以新的 plan 替換未播放尾段，非完整版無限接續。首版不建立長期 taste profile。

## 分階段交付

### M0／G1：可評審手機介面

使用顯式 fixture 覆蓋成功、等待、部分成功、錯誤、播放限制。資料無音訊時顯示模擬，不是可播承諾。主操作與詞彙先固定，不需 key。

### M1／G2：核心電台可用

使用經查核可做本用途的音源，完成真實選歌、檢核、短串詞、TTS、播放狀態機與手機真機驗證。無 DB；Show 保存在 session，重新啟動會明示失效。只快取授權允許的 TTS，不快取 Spotify 音樂。

### M1-S／G3：Spotify 條件式接入

保留原始整合需求，但不保證 Spotify 可承載完整 DJ 願景。先確認用途，再實測允許的搜尋、授權與播放。Spotify 不允許的部分不是靠 mock 宣稱完成。若只能 external-link 模式，產品如實顯示「到 Spotify 收聽」，不能顯示本地進度。

### 階段 1：日常使用

SQLite、存 Show、使用者自行提供的偏好、點歌隊列與節目單分離、預生成、有限接續、手機私有存取環境。使用資料必須符合來源權利與刪除規則。

### 階段 2：個人化

場景、不同 DJ 語氣、具可靠 BPM 的舞蹈編排、經授權的上下文。Spotify 收藏與歷史建立品味不直接啟用；另行政策檢查。

### 階段 3：產品化

多使用者、分享「清單」而非複製音訊、配額／收費假設、公共發佈。平台核可、音樂權利、商業模式需獨立確認；咖啡店／舞蹈教室播放不是一般 Premium 的自動延伸。

## 非功能需求（本次提出的驗收目標）

- 按下操作後 100ms 內有視覺回饋；provider latency 不列為已實測保證。
- 生成 1 秒以上就顯示可取消的進度階段，不能偽造百分比。
- 20 秒仍在等時顯示較長等待提示；總任務預設 60 秒截止。失敗可重試，舊請求不得覆寫新請求。
- 360 CSS px 起核心操作無水平卷軸；320 寬、低高度與 200% 文字放大可垂直捲動完成任務。
- 所有主要點擊區 ≥48×48 CSS px，播放主鍵 64×64；正文 16px。這是本產品目標，不冒稱 WCAG AA 強制 48px。
- 不把第三方失敗丟成原始英文 JSON；每個錯誤均有原因、狀態與下一步。
- 真實裝置的音訊／中斷／恢復為 release gate，不靠模擬器代替。

## 成功指標與限制

產品研究：使用者能說出至少一個選歌理由；能在不離開收聽頁完成暫停、下一首、改感覺；對 Bridge 的「具體且可信」評分。工程驗收：fixture 五首全可執行、無重複串詞、無雙播；真實解析不足五首如實顯示。

原始「90 秒 demo、至少四首可播」保留為 demo 指標，不當作正式穩定度標準。不以 Spotify-derived 播放資料建立分析產品；任何正式產品事件分析需完成資料來源政策審查。
